# PlayLink

PlayLink is a responsive sports-community application built with React, Vite, and Supabase. Players can discover owner-published venues, events, teams, and player listings; venue owners can manage listings, bookings, schedules, and messages.

## Run locally

```sh
npm install
npm run dev
```

## Venue finder and maps

The player-facing venue finder and **Nearby Venues** page display an interactive OpenStreetMap-based map and driving route without opening Google Maps. Owner venues use their saved coordinates; suggested directory places are geocoded when selected. The map uses OpenFreeMap tiles, OpenStreetMap Nominatim for suggested-place lookup, and the public OSRM routing service; routing requests include the user's chosen current location. Venue cards use the owner's uploaded photo when available; otherwise, futsal (and dual-sport) listings use `public/sports/default-futsal.jpg`, and cricket listings use `public/sports/default-cricket.jpg`.

## Supabase authentication

Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` in `.env.local` to your Supabase project URL and **publishable** (or legacy anon) key. These are intended for browser use; never put a Supabase secret/service-role key in a `VITE_` variable. Restart the dev server after changing environment variables.

Local environment files matching `.env.*` are ignored by Git (except `.env.example`). Vite embeds every `VITE_` value in the browser build, so treat those values as public. Supabase publishable/anon keys are designed to be public and rely on database row-level security for protection; service-role keys, database passwords, and other secrets belong only in Supabase Edge Function secrets. Supabase Auth manages password hashing; PlayLink never stores plaintext passwords in its database.

Enable Email/Password in Supabase Authentication and require email confirmation. Add `http://localhost:5173/dashboard`, `http://localhost:5173/reset-password`, and the corresponding deployed URLs to the Auth redirect allow list. Registration sends an OTP first, with a separate sign-in-link fallback. Password recovery sends an OTP and does not offer a reset-link fallback. Login uses email address and password.

For signup OTP emails, update the Supabase **Confirm signup** template to include `{{ .Token }}`. For password-recovery OTP emails, update the **Reset password** template to include `{{ .Token }}`. Set the email OTP length to 6. The signup fallback sign-in link is generated by the `send-auth-fallback-link` Edge Function and sent through Resend. Configure production email delivery before using real accounts; Supabase's default mail service is rate-limited.

OTP entry in signup and password recovery uses a penalty-kick challenge over the supplied stadium/goal background: draw a path from the stationary ball to a numbered 3D block, then release to send the ball along that path. The selected block breaks; its digit animates above the goal for about two seconds before flying into the next OTP slot. Tap an entered digit to remove it and later digits. The challenge has a two-minute timer and offers only a resend action at timeout; requesting a new code does not change the server-side expiry policy.

Set **Authentication → Sign In / Providers → Email → Email OTP Expiration** to **300 seconds (5 minutes)** in the hosted Supabase dashboard. Supabase Auth enforces this validity period for both signup and password-recovery codes; the challenge timer is only for entering the code and does not replace or extend server-side expiration. `supabase/config.toml` includes the same `otp_expiry = 300` setting for local Supabase development. Supabase's email OTP expiry setting also affects the validity of other Auth email links, so review the impact before changing a production project.

To enable the signup-link fallback, verify a domain you control in Resend, create a Resend API key, and configure the Edge Function secrets (never add these to a `VITE_` variable):

```sh
npx supabase secrets set RESEND_API_KEY=<resend-api-key> RESEND_FROM_EMAIL="PlayLink <no-reply@your-verified-domain>" PLAYLINK_ALLOWED_ORIGINS="http://localhost:5173,https://your-deployed-domain"
npx supabase functions deploy send-auth-fallback-link
```

Replace the sender and origins with your verified sender address and exact app origins. The existing security-hardening migration provides the rate-limit RPC used by this public fallback endpoint; apply checked-in migrations with `npx supabase db push` before deploying. Resend only permits sending from a domain you control and have verified; users may receive the OTP/link at Gmail or another supported recipient address. Signup fallback links require the user to re-enter the password they used at signup.

### Apply the profile schema

Apply the checked-in profile migration and deploy the Edge Function before using account creation with unique usernames or username-based login:

```sh
npx supabase login
npx supabase link --project-ref <project-ref-from-your-supabase-url>
npx supabase db push
```

Alternatively, paste `supabase/migrations/20261003000000_profiles.sql` into the Supabase SQL Editor and run it.

Registration currently offers **Player** and **Venue owner** account types. The app supports email-address/password sign-in, OTP-verified registration with a sign-in-link fallback, OTP-verified password recovery, Google sign-in, and a session-protected `/dashboard`. The Google sign-in button is always shown; enable the Google provider and configure its client ID and secret in Supabase Authentication before using it. Add the deployed and local `/dashboard` callback URLs to Supabase's redirect allow list. There are no demo accounts or seeded demo listings.

To configure Google sign-in, create a Web OAuth client in Google Cloud Console. Add Supabase's callback URL (`https://<project-ref>.supabase.co/auth/v1/callback`) as an authorized redirect URI in Google Cloud, then enter the OAuth client ID and secret under **Supabase → Authentication → Providers → Google** and enable the provider. Set the Supabase Site URL and add both `http://localhost:5173/dashboard` and your deployed `/dashboard` URL under **Authentication → URL Configuration → Redirect URLs**. New Google accounts are sent to PlayLink profile completion to choose Player or Venue owner and enter their details. Google verifies the email, and the user sets a password for future email/password sign-ins without an additional OTP step. Apply `supabase/migrations/20261003094000_oauth_profile_username.sql`, `supabase/migrations/20261003095000_optional_oauth_owner_venue.sql`, and `supabase/migrations/20261003100000_google_onboarding.sql` in timestamp order.

Apply `supabase/migrations/20261003095000_optional_oauth_owner_venue.sql` if a Google-created account has owner account metadata but does not include the venue details required by the email registration form. The account can then complete sign-in and add the venue later from its owner dashboard.

### Phase 3: persistent events and match requests

The Events page reads and writes event data through Supabase. Before using it, apply the existing profile migration and then the additive Phase 3 migration:

```sh
npx supabase db push
```

The migration is `supabase/migrations/20261003010000_events_and_match_organization.sql`. It creates `events`, `event_teams`, and `event_join_requests`, with read-only client table grants, RLS, and security-definer RPCs for event creation, requests, approval/rejection, edits, cancellation, completion, and withdrawal. Request approval locks the event row, checks capacity, then updates the request and inserts the team participation within the same database transaction. Capacity status is recalculated by a database trigger.

Profiles whose database `account_type` is `player`, `team_organizer`, or `venue_owner` may create events or submit a team request. After the base Phase 3 migration, apply `supabase/migrations/20261008180000_player_event_creation.sql` to update the database-side role check; without it Supabase still returns `organizer_role_required` for player accounts even though the event form is available. If that error appears, run this migration in the Supabase SQL Editor (or run `npx supabase db push`) and reload the app. The migration also preserves organizer and venue-owner access. The base migration removes direct authenticated updates to `profiles.account_type`; users retain update permission for username, display name, and phone. Signup creates the profile role from account metadata through the existing trusted auth-user trigger. Local demo sessions cannot publish events or request to join.

This checkout does not contain a verified venue table or active-venue schema, and the remote REST schema could not be inspected. Phase 3 therefore stores an organizer-entered `location_text`; it does not invent a `venues` foreign key or suggest that event locations are booked. Team participation uses a team name and its organizer's account because this project has no persistent teams or membership model. Membership is not independently verified.

The migration is additive and does not replace unrelated tables. Back up/export event records before any rollback. Prefer a forward-only corrective migration in production; only remove the three new tables after confirming their records are no longer needed and dropping their dependent triggers, policies, and RPC functions. Do not use `CASCADE` against the shared schema.

### Venue owner workspace

Account creation offers **Player** and **Venue owner**. Venue owners enter their venue profile during signup; `20261003080000_owner_venue_signup_profile.sql` installs the auth trigger that creates the initial venue with the account, including when email confirmation is enabled. On login, PlayLink reads the signed-in user's account type from their profile and sends venue owners to `/owner`; `/dashboard` is role-aware. Sign-in uses the account email address and password. Apply `supabase/migrations/20261003050000_venue_owner_workspace.sql`, `supabase/migrations/20261003060000_venue_booking_requests_and_reviews.sql`, `supabase/migrations/20261003070000_venue_owner_messaging.sql`, and `supabase/migrations/20261003080000_owner_venue_signup_profile.sql` after the earlier migrations. Active owner listings appear on the player Venues page; players can request a date and time range, then view whether the owner accepts or rejects it. Requests are private to the player and venue owner under row-level security. Owners can create/edit venue details, add weekly time slots, manually record bookings, accept/reject player requests, mark an accepted booking completed after play, and set hourly prices. When the owner workspace is open, its bell notification panel checks for new player requests every 15 seconds and links directly to bookings. This is an in-app notification; email and browser push notifications are not configured.

For player-to-owner chat, apply `supabase/migrations/20261003070000_venue_owner_messaging.sql`, `supabase/migrations/20261003091000_venue_message_reactions.sql`, and `supabase/migrations/20261003092000_expand_venue_message_reactions.sql` in order. Players open **Message owner** from an active owner-listed venue to start a private conversation. Venue owners can read and reply to all their player conversations from the **Inbox** in the owner sidebar. Conversation, message, and reaction access is limited to participants by row-level security; the inbox refreshes messages every six seconds while open. Message and description fields have fixed dimensions and scroll internally; the message composer retains its emoji picker and reaction support. Each message has a reaction icon that opens a picker with a wider set of general and sports emojis. Browser-local player and owner demos share demo conversations and reactions only in the same browser.

Signed-in accounts also have a persistent **PlayLink Team** conversation at the top of `/messages`. New-account welcome messages and admin warnings appear there, and replies are saved in `player_inbox_messages`; the dashboard no longer has a separate feedback composer.

Moderation warnings and appeal decisions also appear in the player's bell **Notifications** list and link to **Messages**. In the PlayLink Team conversation, the **Warnings and appeals** section lets a player submit one written appeal per warning. Admins review appeals from **Warning appeals** in `/admin`, can uphold or reverse a warning, and may include a response. Reversing a warning removes it from the active escalation count; the appeal decision is saved as a message and notification for the player. Apply `supabase/migrations/20261008200000_moderation_warning_appeals.sql` after `supabase/migrations/20261008190000_reports_moderation_and_player_events.sql`.

### Reports and account moderation

Apply `supabase/migrations/20261008190000_reports_moderation_and_player_events.sql` after the profile, events, admin, and inbox migrations. Players can report other player profiles and either side of a venue conversation can report the other account. Reporters choose a reason and may include context; reports are retained and sent to the admin-only **Reports** queue. Admins may dismiss reports or issue the next recorded sanction for an account: actions 1–3 are warnings, action 4 suspends sign-in for 3 days, action 5 for 7 days, and action 6 and later permanently suspend the account. The decision and count are stored in moderation tables and a message is saved in the affected user's PlayLink Team inbox. The app checks active sessions against the account restriction, while Supabase Auth suspensions are also applied through the trusted Edge Function.

Deploy the function after setting Supabase's normal `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` Edge Function secrets (the service-role key must never be exposed to the browser):

```sh
npx supabase functions deploy apply-playlink-restriction
```

Set `PLAYLINK_ALLOWED_ORIGINS` as an Edge Function secret to a comma-separated, exact-origin allowlist for the deployed site (for example, `https://playlink.example,https://www.playlink.example`). Do not use `*`; the account-creation, restriction, and username-login functions reject browser origins that are not explicitly listed. Add local origins only to a local Supabase Functions environment when developing locally.

The Reports page marks a recorded suspension whose Auth ban failed and lets an administrator retry it. Apply the migration and deploy the function before enabling report review in production.

### Admin-created accounts, venues, and sports

Apply `supabase/migrations/20261010000000_admin_managed_users_venues_and_sports.sql` after the other migrations. Deploy `admin-create-playlink-account` with `npx supabase functions deploy admin-create-playlink-account`. From `/admin`, an authorized admin can create a player or venue-owner account, add a venue for an existing owner, and add sports. Admin-created accounts are immediately email-confirmed; no verification email is sent. The admin supplies a temporary password and must hand it to the account holder securely. Email addresses and usernames must be unique. Account holders can use the existing verified password-recovery flow later. Creating a venue-owner account also creates its first active venue; further venues can be added from the admin Venues section. Any player or venue owner can create and manage teams and organize events.

For security hardening, apply `supabase/migrations/20261010112000_security_hardening.sql` after the feature migrations and deploy the Edge Functions again. It enables hashed-key, database-backed rate limits for username sign-in, account creation, and applying account restrictions; sign-in is limited to 10 attempts per username and 60 attempts per Cloudflare client IP per 15 minutes. JSON endpoints reject oversized bodies and enforce their content type. CORS is restricted by `PLAYLINK_ALLOWED_ORIGINS`. The Vite development and preview servers bind to `127.0.0.1` by default, and production builds omit source maps. `public/_headers` supplies a content security policy and browser security headers for static hosts that support the `_headers` file format (including Cloudflare Pages and Netlify); configure equivalent response headers in other hosting platforms.

The sports catalog is shared by public listings, venue-owner tools, player/team listings, events, and sport filters. Admin profiles are excluded from the admin user directory and its registered-user count, as well as the public player directory.

While signed in to a player or owner dashboard, PlayLink checks for new messages and booking activity every ten seconds and shows an in-app toast when new activity arrives. Player dashboards also include notifications for recently published events and public teams. Red numbered badges (capped at `9+`) remain on Notifications, Messages/Inbox, and Bookings until the relevant panel or page is opened. Player booking status changes are detected on the next dashboard check; opening Messages or the Inbox marks incoming chat notifications as read. The admin bell refreshes a platform-wide feed every ten seconds, including new accounts, events, teams, reports, appeals, bookings, reviews, player messages, and venue listings.

The owner venue form offers the supplied Kathmandu, Lalitpur, and Bhaktapur futsal/cricket directory in `src/data/venueDirectory.js`; choosing an entry fills its sport, district, address, and Google Maps search link. Owners may also enter a venue not in that directory. The directory does not supply booking availability or prices, so owners must provide those. A local-development-only `venueowner` demo previews owner screens with browser-local sample data; it is not a real account. Real owner workspace records are stored in Supabase. Players can submit one star rating and written review per booking only after its accepted booking is marked completed; reviews then appear on the venue listing and in its owner's Reviews page. The local player and owner demos share a browser-local sample venue and booking workspace.

Venue photos are selected directly from the device during venue-owner signup or from **Your Venue** in the owner workspace; no photo URL is needed. JPEG, PNG, and WebP files up to 5 MB are supported, with a local preview before saving. Supabase accounts store photos in the public `playlink-venue-photos` bucket; venue owners can manage their own photos, and allowlisted admins can upload photos when creating venues on behalf of an owner. Existing projects that already applied the earlier migrations should run `supabase/migrations/20261003101000_venue_photo_storage.sql` and `supabase/migrations/20261010000000_admin_managed_users_venues_and_sports.sql` to enable owner and admin uploads.

### Admin dashboard

The protected `/admin` dashboard shows complete profile details and photos, owner-listed venues, booking requests, venue reviews, and the report queue. Admins can create and manage users, sports, and fully detailed venue listings, and can start or reply to direct-message conversations with any member from **Messages**. The player and venue-owner dashboards have a separate **Contact admin** button that opens their direct support conversation. Admin authorization is held in `public.playlink_admins` and checked by the `is_playlink_admin()` database function and row-level security policies; admin access is never granted from signup metadata or a client-selected role. Apply `supabase/migrations/20261003090000_admin_dashboard_access.sql`, `supabase/migrations/20261008170000_player_admin_profiles_and_inbox.sql`, `supabase/migrations/20261008190000_reports_moderation_and_player_events.sql`, `supabase/migrations/20261008200000_moderation_warning_appeals.sql`, `supabase/migrations/20261008210000_directory_admin_exclusion_and_notifications.sql`, and `supabase/migrations/20261010000000_admin_managed_users_venues_and_sports.sql` in timestamp order. A confirmed Supabase Auth account for `aayushfourth@gmail.com` is automatically allowlisted and routed to `/admin` after sign-in. The password is managed by Supabase Auth and is not stored in the frontend. Other administrators can be explicitly allowlisted from the SQL Editor:

```sql
insert into public.playlink_admins (user_id)
values ('<the-auth-user-uuid>')
on conflict (user_id) do nothing;
```

Sign in with that account and open `/admin`. Admins can pause or reactivate venue listings and use Messages to contact users directly. To revoke admin access, delete only that account's row from `public.playlink_admins`.

### Dashboard profile, location, and avatar setup

Apply `supabase/migrations/20261003020000_dashboard_profile_enhancements.sql` and then `supabase/migrations/20261003030000_profile_username_and_location.sql` after the original profile migration (and after the Phase 3 migration if event notifications should be available). These add editable player details, social profile URLs, private saved coordinates, username availability/suggestion RPCs, the required profile update grants, and the public `playlink-avatars` image bucket. Use `npx supabase db push` for a linked project, or run the migrations in timestamp order in the Supabase SQL Editor.

`/profile` lets a signed-in player update their display name, unique username, profile photo, home area, player bio, sport, position, experience level, and any combination of Instagram/Facebook/TikTok profile URLs. Username checks exclude the current user, while a case-insensitive unique index prevents duplicate usernames including concurrent changes; available alternatives are suggested on conflicts. Usernames identify public PlayLink profiles; sign-in uses the account email. Avatar uploads are limited to JPG, PNG, or WebP and 5 MB for Supabase accounts (2 MB in local demo mode). Only supplied social links are shown as icons. The public player directory exposes registered player's display names, usernames, photos, and linked social accounts; other profile details and precise coordinates remain protected unless included in a published player listing. The local demo profile is browser-only and cannot check username availability against real PlayLink accounts. If RLS or storage denies changes, check the migration before retrying.

The Players directory shows registered player accounts with their profile photos and any linked Instagram, Facebook, and TikTok icons; unlisted accounts use their profile details until they publish a full player listing. Social URLs are exposed to other users only for these public player profiles. The designated admin account is excluded from both public player listings and player-invite search, even if its profile is marked as a player. Apply `supabase/migrations/20261008170000_player_admin_profiles_and_inbox.sql` after the community/profile migrations, then apply `supabase/migrations/20261008210000_directory_admin_exclusion_and_notifications.sql` to install the admin exclusion and live notification RPC. A database trigger also saves the PlayLink welcome message for each new profile. It appears in the PlayLink Team conversation in Messages. Inbox messages cannot be deleted through the client.

Player profile details have a **Message player** action that opens a private, persistent conversation in the dashboard inbox. Both participants can continue the conversation from **Messages**; row-level security limits access to the two participants. Apply the additive `supabase/migrations/20261004102000_player_direct_messaging.sql` migration to enable player-to-player chats.

Any signed-in player can create a team, optionally search active player listings by username or display name to invite a player during creation, and choose whether the team is public. Any signed-in user can request to join a public recruiting team with open spots; a published player listing is not required. Team owners can edit or delete their teams from the team details view, invite players later from a player profile, make a team public or private, and review public join requests under **Teams → Invitations** or dashboard notifications. Owners can view a restricted profile summary for a pending requester; contact information and private account data are not exposed. Deleting a team also removes its invitations, join requests, memberships, and group chat. Invited players accept or reject invitations there; team owners accept or reject join requests there. Acceptance creates membership and grants group chat access to the team owner and accepted members only. Apply `supabase/migrations/20261004103000_team_invitations_and_group_chat.sql`, then `supabase/migrations/20261004104000_public_team_requests.sql`, followed by `supabase/migrations/20261004105000_team_days_and_invite_player_search.sql`, `supabase/migrations/20261004106000_team_join_without_player_listing.sql`, and `supabase/migrations/20261004107000_team_request_player_profiles.sql`, after the community listings migration. These later migrations add team available-day storage, a restricted username-search RPC, requests without requiring a published player listing, and owner-only profile summaries for pending requesters. If earlier team migrations have already succeeded, run only migrations not yet applied, in timestamp order. In the Supabase SQL Editor, run the full contents of each missing migration as one query.

The dashboard location control requests browser geolocation only after the player selects **Use live location**. The map centers on those coordinates using OpenStreetMap-based tiles; coordinates are sent to the OpenStreetMap routing service only when calculating a route. Coordinates are reverse-geocoded to a readable place name through OpenStreetMap's Nominatim service; this also sends the opted-in coordinates to that service. **Save location** stores both the place name and coordinates on the player's profile (or in local storage for the demo account). The saved place name appears in the dashboard header and profile basic information, where the player can edit it. Raw coordinates are retained only for map display and directions, not shown as the location label. The notification popover displays persisted event join requests and status changes for events the player requested to join or organizes. It requires the Phase 3 migration and is not a general-purpose notification service.

## Live cricket and football scores

The `/live-scores` page and player, venue-owner, and admin dashboards show CricketData.org current/live cricket matches plus Sportmonks cricket fixtures scheduled in the next 30 days and completed results from the previous three days. When CricketData.org returns Nepal Premier League matches in its current-match response, the page includes live matches, upcoming games in the next 30 days, and recent results from the previous three days; those matches are not available while CricketData.org is unreachable. Cricket cards show provider-supplied team crests or flags when available, with initials as a fallback. Football live matches, fixtures, and recent results come from football-data.org. API-Football supplies a fallback for goal, card, and substitution events when football-data.org omits them; it is requested only when a user opens a played match, and only used after matching the date, both teams, and (when available) final score. Football coverage depends on the competitions available to the football-data.org account and event coverage available to the API-Football account. Provider keys are read only by the `sportmonks-live-scores` Supabase Edge Function; never add them to `.env.local`, a `VITE_` variable, or browser code. Store `CRICKETDATA_API_KEY`, `SPORTMONKS_API_TOKEN`, `FOOTBALL_DATA_API_TOKEN`, and `API_FOOTBALL_KEY` in the Supabase project's Edge Function secrets. Cricket requests are cached for up to 20 minutes to stay within CricketData.org's published free allowance of 100 hits per day.

Deploy the function to the same Supabase project configured in `VITE_SUPABASE_URL`:

```sh
npx supabase functions deploy sportmonks-live-scores
```

The authenticated score function permits secure HTTPS app origins and localhost development origins; authorization is enforced using the signed-in Supabase user token. Cricket uses CricketData.org's documented `currentMatches` endpoint for current matches; upcoming fixtures and recent results still depend on Sportmonks Cricket API v2. Football uses football-data.org's v4 matches endpoint with the API token sent in the `X-Auth-Token` header; returned live matches, fixtures, and recent results are limited to the competitions available to the account. Recent football results are ordered newest first; opening a result fetches and caches match details, including goals, scorers, minutes, assists, score by period, bookings, substitutions, venue, officials, team statistics, line-ups, benches, and formations when the provider supplies them. If goal, booking, or substitution events are missing, the function uses API-Football's v3 fixtures/events endpoints with `API_FOOTBALL_KEY`, first matching the fixture by date, home and away team, and final score where available. The fallback is used only for the opened match and its events are merged without replacing football-data.org details. Standings and head-to-head history load on demand in their themed match-detail tabs to reduce unnecessary API usage. Provider errors and unavailable fields are identified rather than replaced with invented data.
